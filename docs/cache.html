缓存管理

缓存系统概述

Lingcoo WebSocket Push 插件的缓存管理系统负责在 WordPress 内容发生变化时，自动失效 Next.js 前端应用的相关缓存。这确保了前端始终显示最新的内容，同时保持了缓存带来的性能优势。

缓存失效机制

标签缓存失效 (Tag-based Revalidation)

使用 Next.js 的标签缓存系统，通过特定的标签来标识和失效相关的缓存内容。

API 端点
POST http://frontend:3000/api/revalidate
Headers:
  x-revalidate-secret: YOUR_REVALIDATE_SECRET
Body: cache_tag_name

路径缓存失效 (Path-based Revalidation)

直接失效特定路径的缓存，适用于需要立即更新的页面。

API 端点
POST http://frontend:3000/api/revalidate-path
Headers:
  x-revalidate-secret: YOUR_REVALIDATE_SECRET
Body: /path/to/page

缓存标签分类

文章相关缓存标签

post:{shortUuid} 特定文章的详情页缓存
page:{slug} 特定页面的缓存
homepage-posts 首页文章列表缓存
post-type:{post_type} 特定文章类型的列表页缓存

分类法相关缓存标签

category:{slug} 特定分类的页面缓存
category-index-page 分类索引页缓存
tag:{slug} 特定标签的页面缓存
tag-index-page 标签索引页缓存
taxonomy:{taxonomy} 自定义分类法索引页缓存
taxonomy-term:{taxonomy}:{slug} 自定义分类法条目页缓存

缓存失效触发场景

文章操作触发的缓存失效

文章更新

触发条件: 文章内容、标题、状态等发生变化

失效缓存:

  • 文章详情页: post:{shortUuid}
  • 首页列表: homepage-posts
  • 相关分类页: category:{slug}
  • 相关标签页: tag:{slug}
  • 自定义分类法页: taxonomy-term:{taxonomy}:{slug}
文章发布

触发条件: 新文章发布或草稿变为发布状态

失效缓存:

  • 首页列表: homepage-posts
  • 文章类型列表: post-type:{post_type}
  • 所有相关分类法页面
文章删除

触发条件: 已发布文章被删除

失效缓存:

  • 首页列表: homepage-posts
  • 所有相关分类法页面
  • 文章类型列表页

分类法操作触发的缓存失效

标签更新

触发条件: 标签被创建、编辑、删除或元数据更新

失效缓存:

  • 标签索引页: tag-index-page
  • 特定标签页: tag:{slug}
  • 标签页路径: /tag/{slug}
分类更新

触发条件: 分类被创建、编辑、删除或元数据更新

失效缓存:

  • 分类索引页: category-index-page
  • 特定分类页: category:{slug}
  • 分类页路径: /category/{slug}
自定义分类法更新

触发条件: 自定义分类法条目被创建、编辑、删除

失效缓存:

  • 分类法索引页: taxonomy:{taxonomy}
  • 特定条目页: taxonomy-term:{taxonomy}:{slug}
  • 分类法路径: /taxonomy/{taxonomy}
  • 条目路径: /taxonomy/{taxonomy}/{slug}
文章分类法关联变化

触发条件: 文章的标签、分类等关联发生变化

失效缓存:

  • 所有受影响的分类法页面
  • 相关的索引页面

缓存失效策略

智能失效

  • 关联分析 - 自动分析内容变化影响的所有相关页面
  • 批量处理 - 将相关的缓存失效操作批量执行
  • 去重优化 - 避免重复失效相同的缓存标签
  • 优先级处理 - 优先处理用户可见度高的页面缓存

性能优化

  • 非阻塞请求 - 缓存失效请求不阻塞 WordPress 操作
  • 错误容忍 - 缓存失效失败不影响 WordPress 正常功能
  • 超时控制 - 设置合理的请求超时时间
  • 重试机制 - 对失败的请求进行适当重试

配置和自定义

自定义前端服务器地址

// 在主题的 functions.php 中添加
add_filter( 'fd_websocket_push_frontend_url', function( $url ) {
    return 'http://your-frontend-server:3000';
} );

自定义缓存标签

// 添加自定义缓存标签失效
add_action( 'your_custom_event', function() {
    $cache_invalidator = FD_WebSocket_Push_Cache_Invalidator::get_instance();
    $cache_invalidator->revalidate_tag( 'custom-cache-tag' );
} );

禁用特定缓存失效

// 禁用文章相关的缓存失效
add_filter( 'fd_websocket_push_enable_post_cache_invalidation', '__return_false' );

// 禁用分类法相关的缓存失效
add_filter( 'fd_websocket_push_enable_taxonomy_cache_invalidation', '__return_false' );

监控和调试

日志记录

插件会记录所有缓存失效操作的详细日志：

# 成功的缓存失效日志
[Lingcoo WebSocket Push] Revalidate tag queued: homepage-posts
[Lingcoo WebSocket Push] Revalidate path queued: /category/technology

# 错误日志
[Lingcoo WebSocket Push ERROR] REVALIDATE_SECRET is not defined. Cannot revalidate tag: homepage-posts

调试模式

启用 WordPress 调试模式以获取更详细的日志信息：

// 在 wp-config.php 中添加
define( 'WP_DEBUG', true );
define( 'WP_DEBUG_LOG', true );

🔧 最佳实践

  • 确保 REVALIDATE_SECRET 与前端应用配置一致
  • 监控前端应用的缓存失效 API 响应时间
  • 定期检查 WordPress 错误日志中的缓存失效相关消息
  • 在高流量网站上考虑使用队列系统处理缓存失效
  • 测试环境中验证缓存失效是否按预期工作
